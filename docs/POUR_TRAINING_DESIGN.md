# 倒水任务:通用训练设计(Video Prior 驱动)

**日期** 2026-08-14 　**状态** 草案待审 　**基准数据** `egodex/test/pour/17`
**目标** 同一任务内**对物体泛化**——换一只杯、换一个瓶,同一套代码与配方直接跑通。
**上游依据** `NOISY_WORLD_FRAMEWORK.md` P1~P5;`CONFIDENCE_GUIDE.md` §3(RL 消费契约);
`KEYFRAME_PRIOR_DESIGN.md`(拧盖任务的 KeyFrame 编译框架,本设计复用其机制并按倒水任务改造)。

## 0. 一句话

**把"倒水"从"模仿一条手部轨迹"重写成"让两件容器的功能几何达成一个相对关系"**:
Video Prior 负责说清 *谁拿什么、什么时候、大致怎么摆*,
sim 的功能几何(开口盘、倒出点、落点)负责说清 *成没成*。
前者可以 noisy,后者必须精确 —— 泛化能力来自**判据只依赖功能几何参数,不依赖具体物体**。

## 3. Video Prior 能给什么(pour/11 全链实证)与消费契约

`results/pour_11/` 是同任务已跑通的**零人工**全链样例,直接说明倒水任务的先验清单:

| 先验 | pour/11 实测 | 在本设计里的用途 |
|---|---|---|
| **逐物体接触区间** | 瓶×右 `[19,168]`,杯×左 `[2,168]`;瓶×左/杯×右自动判零跳过 | **手↔物配对与事件时序全自动**(比拧盖的嵌套规则更直接) |
| 逐物体可信度 | 瓶 conf_pos **87**/conf_rot **46**;杯 conf_pos 50/conf_rot **7(弃用)** | 决定每个通道进不进奖励(见下方契约) |
| 接触热区 | 瓶×右 f93(6069 顶点,ring/middle/thumb 握带);杯×左 f85(middle/ring 扶带) | 每只手的 affordance / 参与指集合 |
| 抓握模板计划 | `grasp_template_plan.json`(VLM+几何融合,power/5指/候选排序 5_Light_Tool…) | **每个物体的抓握先验自动生成**(selector v3),泛化的关键一环 |
| 手轨迹 / 物轨迹 | 双手 MANO + 双物体 6DoF 逐帧 | 接近走廊 + 时间轴 |
| σ / manifest | `poseqa/`(逐帧 σ、CT 一致性、take 级裁决) | 逐帧门控 |

**消费契约(照搬 `CONFIDENCE_GUIDE.md` §3,不新发明)**:

```
位置 σ ≤10mm      → 硬用(锚点/RSI/强 tracking)
      10~30mm     → 软用(σ 球内不罚的死区奖励)
      >30mm       → 放开,不给参考
旋转  conf_rot ≥30 且 σ_rot ≤5° → 该帧可用;否则不给
      rotation_usable=false     → 整条通道弃用
      rotation_free_axes        → 该轴永久自由
```

按这个契约,pour/11 的**瓶旋转可用(46)、杯旋转弃用(7)**:
⟹ 瓶的倾角可以进参考,**杯的倾斜不进参考**(人把杯歪 40° 去迎瓶口是工效学解法,不是任务要求;
机器人保持杯大致竖直更稳,判据不关心杯怎么拿)。这是"人的解法不强加"的第二次实战。

## 4. 先回答一个更根本的问题:不写任务特定代码,先验够不够?

**用户质疑(2026-08-14,成立)**:"倒出点=开口环最低点"不是从任何先验推出来的,
**是把倒水的物理写死进代码**——换个任务就作废。据此重审整套设计,把问题拆成两问:

### 4.1 「要做什么」—— 够,已实测验证

拧盖任务的事件抽取靠**接触变化**;但倒水的关键时刻**没有任何接触变化**(两手一直握着),
纯接触驱动的抽取器会**完全漏掉倒水动作**。补一条同样通用的规则即可:

> **关键帧 = 接触变化事件 ∪ 驻留段**;驻留 = 演示在某个**相对构型**上停留
> (相对位姿变化率低于交互窗口内的分位阈,持续 ≥10 帧)。

**pour/11 实测(零倒水知识)**:限定在"两物体都被抓住"的窗口(由逐物体接触给出),
驻留检测**只找出两段,且全部落在倾倒平台**:

| 检出段 | 长度 | 瓶倾角均值 | 瓶杯间距均值 |
|---|---|---|---|
| 帧 [96,106] | 10 帧 | **85.5°** | 20.8cm |
| 帧 [111,122] | 11 帧 | **87.3°** | 20.8cm |

对拍:倾角 >60° 的真实区间是 [78,130] —— 检出段全在其中,**没有误检**。
(首版用全局阈值只捞到"桌面静置",被自身证伪后改为交互窗口内 + 平滑,方为可用。)

⟹ 目标可以完全通用地表述为:**到达并保持演示中那个高可信的相对构型**
(按 §3 契约门控:pour/11 = 相对位置 + 瓶朝向可用,杯朝向弃用)。
保持时长也直接读驻留段长度。**同一条规则对拧盖(拧转平台)、放置(松手)一样成立。**

### 4.2 「成没成」—— **不够**,而且原因是结构性的

视频里**没有液体**(不重建、常常也看不见)。若只要求"复现演示的相对构型 ±容差",
容差必须覆盖重建误差(σ 常 1~3cm,pour/11 的杯 mesh 还偏大 2×),
而真杯口半径才 ~4cm ⟹ **一次"达标"的回合可能实际倒在桌上,我们却无从判断**。

根因(值得单独记住):**抓取的关键构型有接触可当"胶水",重建误差会被物理约束吸收;
倒水的关键构型是"无接触的空间关系",没有任何物理约束能吸收误差。**
这是倒水比抓取更难被先验钉住的本质原因,不是工程疏忽。

### 4.3 任务知识不可能为零 —— 问题是它**住在哪**

| 方案 | 任务知识住在 | 泛化性 | 成本 |
|---|---|---|---|
| **A. 语义判据**:渲染 rollout 交 VLM 与原视频对拍 | **通用机制**(框架任务层本来就这么定义) | ✅ 每个任务同一套 | 贵,不能逐步跑 ⟹ 用于**评测**与校准 |
| **B. 物理内生**:sim 里给源容器装"内容物"标记粒子,成功=内容物进了目标容器 | **数据**(哪个是源/有内容物,由 VLM/LLM 层给;数据集自带 `llm_verbs:['pour']`、`llm_objects`),物理由引擎负责 | ✅ 对"转移类"任务通用 | 中,可只放少量标记粒子 |
| **C. 落点几何**(本文档原 §6 写法) | **手写代码** | ❌ 换任务作废 | 便宜、最稠密 |

#### A 方案的时间分辨率与采样预算(2026-08-14 查实,用户提问触发)

**VLM 不"看视频",它看的是抽样出来的一叠静止画面** —— 这决定了它能判什么、判不了什么。
我们管线现成参数(`steps/step3_grasppose/vlm_grasp_schema.py`):叠加片 `stride=4`/`out_fps=4`,
调用时 `mm_processor_kwargs={"fps":2.0}`。对 pour/17(142 帧 @30fps,4.73s)实算:

| | 人眼 | 我们的 VLM |
|---|---|---|
| 实际看到的画面 | 142 张(连续) | **≈18 张** |
| 相邻画面间隔 | 1/30 s | **≈0.26 s(≈8 原始帧)** |

⟹ ①**短于 ~0.26s 的事件会掉进采样缝**(倒水平台 1.5s 安全;"洒了一下""杯被碰歪"可能漏);
②延迟与视频长度基本无关、只与抽帧数有关(5s 与 60s 同价),但单次调用不快
(仓内调用 `timeout=900`);③**判官不能进逐步回路** —— 2048 回合确定性评测不可能逐条问 VLM。

**因此 A 方案的用法定为**:评测期抽样(数十~百回合)当判官;
**采样预算集中到驻留段**(§4.1 已经算出关键段在哪,不必均匀看全程)——
同样预算下关键时刻的时间分辨率可提高数倍。
**可靠性有实测**:同一 VLM 在抓取描述任务上与人工一致率 **92.6%**(active_hand 95.8%,100 clip)
⟹ 当评测判官够用;**当逐步训练信号是毒药**(P5:可信度标错比没有更糟)。

**裁定**:训练目标走 4.1 的通用表述;**成败判据走 A/B(通用),不走 C**。
C 降级为**可选的稠密塑形项**,且必须可证伪 —— 见 §9 的 A/B 对照实验。

注意:去掉 C **并不会丢失稠密性**(到"演示相对构型"的距离本身就是稠密信号);
丢的是**目标的准度**。这正是要用实验回答的问题。

## 4bis. 功能几何(仅在 C 臂/资产库路线启用)

奖励与判据**一律不写具体物体的坐标**,只写两组功能参数;换物体只是换参数值:

| 角色 | 参数 | 怎么自动得到 |
|---|---|---|
| **源容器**(瓶) | 长轴 `a_src`、开口环 `R_src`、**倒出点 `p_spout`** | 长轴=网格 OBB 最长轴;开口端=①横截面积更小的一端(瓶颈)②**倾倒时离目标更近的那一端**(视频先验,pour/11 实测 13cm vs 29cm,判别显著);**倒出点 = 开口环在世界系中 z 最低的那个点**(随姿态逐步重算) |
| **目标容器**(杯) | 开口盘:中心 `c_dst`、半径 `r_dst`、法向 `n_dst` | 开口端=横截面积更大的一端;半径=该端截面等效半径;法向=长轴方向(静置时应与重力一致,可自检) |

**为什么"倒出点=开口环最低点"是通用定义**:瓶颈细 ⟹ 最低点就是壶嘴;碗口宽 ⟹ 最低点就是
倾倒时的溢出边;杯倒杯也成立。**不需要知道物体是什么,只需要它有一个开口环。**

⚠ **两个已知坑**(pour/11 实测):
1. **mesh 尺度会错**:pour/11 的杯 mesh 16×26cm vs 真实约 8×14cm(多物体轮次选帧所致)。
   开口半径直接决定判据松紧 ⟹ 功能几何**必须过尺度自检**(`pose_audit.mesh_scale_fitted` +
   稳定静置高度对拍);不过关就走 **CAD 替身**(本条数据的 Proud Source 瓶**仓内已有 CAD**)。
2. **SAM3D 网格通常是闭合壳**,没有真正的开口边界环 ⟹ 开口环退化为"沿长轴取端部截面",
   用截面积极值定哪端;真开口边界仅在网格带边界时启用。

## 5. 任务文法与里程碑链(从逐物体接触自动推)

事件全部来自**逐物体接触区间 + 物体运动起始**(拧盖任务已验证:物体开始动 = 被抓稳,差 1 帧):

```
K0 站姿
 ├─ [grasp_dst] 左手抓稳杯   ← 杯×左接触起始 + 杯开始运动
 ├─ [grasp_src] 右手抓稳瓶   ← 瓶×右接触起始 + 瓶开始运动
 ├─ [lift]      两物体离桌   ← 高度超过桌面 + 支撑消失
 ├─ [align]     会合:倒出点位于杯口上方(相对位姿进容差)
 ├─ [pour]      倾角 ≥θ 且落点在杯口内, 保持 N 步    ← 主判据
 ├─ [recover]   瓶复位竖直
 └─ [place]     两物体放回桌面(位置由视频给,容差 ±3cm)
```

抓取先后由接触区间起始决定(pour/11:杯 f2 先于瓶 f19)。
`θ`(倾角阈值)不手调:取**视频倾角曲线平台段的分位数**(pour/11 平台 84~90°),
再按功能几何自检(倒出点必须低于源容器开口环中心)。

**顺序门控**沿用冠军机制(§2.14:两技能抢一张网必死,顺序化 6/6 存活):
里程碑逐个解锁,`gate_i = slowEMA(milestone_i) ≥ 0.8` 才放行下一环。

## 6. 奖励与判据(按 §4.3 裁定改写)

**主方案(通用,零任务代码)**:
```
稠密   −dist(当前相对构型, 演示驻留构型)      ← 门控:位置按 σ 分层, 朝向按双门
稀疏   进入容差并保持 ≥ 驻留段时长            ← 里程碑
终止   任一物体脱手 / 撞倒 / 超时
成败   评测期由 A(VLM 对拍) 或 B(标记内容物) 判定, 不进逐步奖励
```
容差 = `tol0 × (1 + k(1−c))`,随该驻留段的可信度放宽(低可信给松容差,不给错目标)。

**下面这段是原设计的任务特定写法,现降级为 C 臂的可选塑形项,默认关闭**:

**不做粒子流体**(1024 env 不可行,且流体参数本身是另一层不确定性)。改用:

```
倒出点   p_spout(t)        = 源容器开口环上世界 z 最低点
落点     p_land(t)         = p_spout 沿重力投影到目标开口盘所在平面
命中     hit(t)            = |p_land − c_dst| ≤ r_dst − margin   ∧  p_spout 高于开口盘
倾倒中   pouring(t)        = tilt_src(t) ≥ θ  ∧  hit(t)
成功     Σ_t pouring(t) ≥ N 步(N 由视频倾倒平台时长给, pour/11 ≈45 帧)
```

- **稠密奖励**:`−|p_land − c_dst|`(会合期)与 `tilt` 斜坡塑形(倾倒期),两者都有界;
- **失败/终止**:任一物体脱手、杯被撞倒(倾角超限)、倒出点在杯口外且倾角超 θ(=洒了)、超时;
- **为什么这比流体更好**:落点判据**逐步可测、天然稠密**,而且换物体只换 `r_dst`——
  流体则要重调粘度/表面张力,且没有对应的先验来源。
- 保留升级路径:如需真实液面,可在**评测期**(非训练期)对冠军 ckpt 做一次粒子复核。

## 7. 阶段课程(每阶段单独批准起训)

| 阶段 | 谁动 | 里程碑 | 达标 | 机制来源 |
|---|---|---|---|---|
| **S1 抓杯** | 左臂(右臂锁站姿) | grasp_dst(+持稳竖直) | 确定性 ≥0.9 | 旧训①同构(接近+抓+持稳) |
| **S2 抓瓶** | 右臂(左臂冻结/低 lr,杯保持在手) | grasp_src | ≥0.9,且 S1 不破 | 顺序门控 |
| **S3 会合** | 双臂 | lift → align(落点进杯口) | align ≥0.7 | 相对位姿目标,容差按 σ 放宽 |
| **S4 倾倒** | 双臂 | pour(θ + 命中 + 保持 N 步)→ recover → place | 全流程 ≥0.5 | 新技能低期待口径 |

**S1/S2 为什么不并行**:虽然两手各有各的物体、不抢同一目标,但共享一张网;
§2.14 的教训是"未巩固的技能会被另一支的失败梯度冲掉"。顺序化代价只是墙钟。

① 左手要去环抱一个直径 15.3cm 的柱体而不是 ~10.5cm —— 可能**因为假原因**学不会抓;
② 碰撞/物理全错;③ L2-phys 判官会"过宽接住"而虚报成功。

### 11.5 更正 §11.3 的理由:真正的门禁是**可抓性**,不是"网格准不准"(2026-08-14)

**用户质疑(成立)**:"直接在重建出来的物体上生成 GraspPose 不行吗?"——**行**。
GraspPose 在哪个网格上生成、sim 就用哪个网格,世界是**自洽**的;抓握在 sim 里就是有效的
(与既有结论一致:模板看接触位置合理性、pp0 八候选全 `ok=false` 照样 99.9%)。
⟹ 我原先"物理不准所以必须修网格"的理由**不成立,撤回**。

**但机器人的手不会跟着网格一起变胖** —— 这才是硬约束。实测:

| 量 | 值 |
|---|---|
| SharpaWave 最大直径模板 `1_Large_Diameter` 接触点包络 | **7.9 × 7.7 cm**(最远两点 11.4cm) |
| 手所有连杆网格合并包围盒 | 9.7 × 8.5 × 15.5 cm |
| 历史成功抓取的最大物体 | Proud Source 瓶身 **6.5cm** |
| **重建杯** | **15.3cm** ⟹ 远超包络,**根本合不拢** |
| **修正后真实杯** | **≈10.5cm** ⟹ **仍超包络**,顶多指尖对置(11.4cm 极限)勉强 |

⟹ **两个结论**:
1. 用胖网格开训,S1 会因为**现实中不存在的原因**失败(不是"抓不好",是生成不出可行抓握);
2. **修网格也救不了** —— 这只手本来就抓不住这只杯子。问题不在数据,在**本体**。

### 11.6 因此新增通用门禁:**可抓性体检**(任务无关)

开训前对每个物体自动跑:`物体可抓尺寸 vs 机器人手抓握包络`,并**让任务文法自动降级**:

```
对每个 (物体, 手):
  若 Dexonomy 在该网格上能合成有效抓握      -> 该物体可拿起, 保留 grasp 里程碑
  否则                                      -> 该物体**留在桌面**, 从文法中删除其 grasp/lift 里程碑,
                                              只保留它作为"环境中的目标"(其余里程碑照常)
```

对 pour/17 的裁定(待 Dexonomy 实证):**杯留在桌面,只训右手拿瓶去倒** ——
任务本质(瓶倾倒对准杯口 + 保持)完全保留,而且"往桌上的杯里倒水"在现实中本就更常见。
这条从 §9 的 P5 **回退方案**升级为**由体检自动裁定的主方案**。

**决定性验证(下一步)**:在胖网格与修正网格上各跑一次 Dexonomy,看能否合成有效抓握。
两者都失败 ⟹ 按上式自动降级,不再纠结网格;修正网格成功 ⟹ 修网格并保留双手抓取。

**网格修正的优先级随之下调**:不再是"开训前必修",而是"影响碰撞体积/判官宽严/未来 sim2real
一致性"的**建议项**;是否修由上面这次 Dexonomy 实证决定。

### 12.3 训练顺序的自动判定(B 的落地,不含任何人工设定)

**顺序来源 = 交互标注 + KeyFrame,按时间排序**,而不是人写阶段表:

```

第 i 阶段 = 解锁到链上第 i 环
阶段推进 = gate_i = slowEMA(第 i 环达成率) ≥ 0.8      # 0.8 是超参, 不是任务知识
```

**pour/17 自动生成的链(2026-08-14 **已订正**,全部为实测帧号)**:

| 5 | **[109,137]** | 静置收尾 | 驻留段② |

⚠ **订正记录**:本表首版写的是"[10] 抓瓶 / [28] 抓杯",**错**。用**物体质心高度曲线**复核发现:
杯在 f36 前平在 94cm、f38 起 96.4→99.2→104.3 才抬起;瓶在 f20 前平在 95cm、f22 起 97.3→99.4。

## 13. 训练范式改版:按人手轨迹「先接近、再交互」(2026-08-15 用户裁定)

**改动**:废除 `grasp_first`(先抓后飞)门控,改为**完全按人手轨迹学**:接近 → 交互 → 收尾。
**GraspPose 降级为软鼓励**,不是硬性条件。

### 13.1 为什么旧理由不再适用,以及换来的新风险

§2.14 的死因是"**两个起步分支共享一张网**"(站姿起步 vs 预抓握起步抢梯度,4/6 死)。
新范式是**单一起点、单条连续轨迹**,竞速对象结构性地不存在。

但换来一个新风险:旧办法里"从预抓握起步"让**接触经验是免费的**;现在接触必须在接近成功
之后才发生 —— 接近学不动 ⟹ 永远见不到接触 ⟹ 抓取项无梯度(稀疏奖励卡死)。

**这次可能行的依据**:当年接近难学很大程度是因为 27 号手轨迹是坏的(腕位差 40cm,
把手引向空桌面);本条数据的手轨迹**经投影核验为准**,跟踪才有意义。
**预注册**:5M 步内接触率仍 ≈0 ⟹ "接近优先"在本设置下被证伪,启用 13.3 的 RSI 退火。

### 13.2 四项裁定(2026-08-15)

| # | 决策 | 裁定 |
|---|---|---|
| 1 | 参考索引 | **相位索引**(参考指针可以"等"策略),不用绝对时间索引 |
| 2 | RSI | **按阶段做**:接近阶段内在人手轨迹上随机初始位置(见 13.3) |
| 3 | GraspPose 软项 | **退火到 0** |
| 4 | 第一条 run | `Pour17_bottle`(右手抓瓶),之后升级到双臂同训 |

### 13.3 阶段内 RSI(用户提案,采纳)—— 为什么它比通用 RSI 安全

> 在**标注的交互开始之前**(接近阶段),沿人手轨迹随机取 t₀ 作为回合起点。

**好处**:接近的难度不均匀 —— 最后 3cm 的对准才是卡点(冠军实测 d_pos 收敛到 4.5cm
就再也过不去 3cm 切换线)。不做 RSI 时,策略必须先学会前 90% 才有机会练最后 10%,
是**串行瓶颈**;阶段内 RSI 让每个回合都可能直接从"快到了"开始练对准。

**为什么比通用 RSI 安全**:接近阶段**物体还没被动过**,初始化只需把手臂/手指摆到参考状态,
物体保持在 layout 摆放位 —— 不需要重现"物体已在手里"的中途状态(那才是脆弱的部分)。

**两个必须的附加条件(台账教训,不可省)**:
1. **RSI 概率必须退火到 0**。固定 rsi_prob 会让策略"只会从中间开始",端到端能力是假的
   (旧账原文:固定 rsi_prob 让策略偷懒只会保持不会从头抓 ⟹ 改课程退火到 0)。
2. **评测口径只认 t₀=0**(`success_rate_t0`)。训练期带 RSI 的成功率**必然高估**。

**一条精化(用我们已有的机器)**:t₀ 不要均匀采样,按**逐帧可信度加权**采样 ——
低可信帧的参考状态本身可能是错的,从那里初始化等于把策略扔进一个不存在的世界。

**交互阶段的 RSI 不在本轮**:那需要"把物体放进手里"的初始化(旧任务的 RSI+freeze 做过,
但脆弱)。本轮只做接近阶段 RSI。

### 13.4 相位索引的具体机制

```
参考指针 φ 按名义速度前进; 但当当前跟踪误差 > 阈值时**暂停前进**(等策略跟上),
暂停有预算上限(超预算即判定该回合落后, 走超时终止);
里程碑达成时 φ 硬推进到下一阶段起点。
```
理由:固定时间索引下,策略慢一点就被永久惩罚 —— 冠军"顶着模仿罚直飞"正是对抗它的表现。
现在我们**要**跟踪,就得让时间轴有弹性。

## 14. 物体 yaw 的裁定:Gate 1c「接近侧对齐」(2026-08-15,用户裁定走 B)

### 14.1 问题:Gate 1 保证的和新范式需要的不是同一件事

`screen_prior` 的 Gate 1 检查的是「**物体朝向与视频一致**」(Δψ ≤ 10°)。
它**不检查**「机器人的手是否从人手那一侧接近」。旧范式(`grasp_first`,策略自己找抓法)
两者都无所谓,所以一直按 IK 可达性自搜 yaw 也没出事;**新范式照着人手轨迹走**,
参考轨迹与 GraspPose 就成了两个会互相拽的权威。

pour/17 实测这两件事差 **108.6°**:参考把手领到方位角 216.0°,GraspPose 落在 316.5°。

物体 yaw **只能对齐其中一件** —— 视频接触带与 Dexonomy 抓法**在物体坐标系里**就差
108°(接触带绕瓶身包约 150°,两者落在同一条带的不同段),转物体不能同时对齐两者。

### 14.2 裁定规则(可测,不是拍脑袋)

| 判据 | 阈值 | 含义 |
|---|---|---|
| `yaw_symmetry_mm`:绕竖轴转 15/45/90/180° 后点云的最近邻中位偏差取最大 | < **5mm**(≈重建噪声量级) | 回转体 ⟹「物体朝哪」在物理上是**空的量**,A 方案在保护一个空的量 ⟹ **走 B** |
| ≥ 5mm | | 朝向有物理意义 ⟹ 走 A(钉死视频 yaw) |

实测:瓶 **0.7mm** / 杯 **3.3mm**,两者都在回转体这一档。

**B 的定义**:`yaw_B = (人手接近方位角 − K) mod 360`,其中 `K = 手腕方位角 − 物体 yaw`
由 GraspPose 自身决定(编码"这个抓法在物体的哪一侧")。

### 14.3 三个必须踩准的实现细节(都踩过)

1. **人手方位角的窗口只能取「接近段末尾」**,不能用整条接触窗 —— 抓住之后手物刚体耦合,
   倒水段物体被倾到 84°,那段的"水平方位角"没有意义。实测整窗中位 193.1° vs 接近段末
   **216.0°**(圆标准差仅 1.2°),差 23°,足以改变裁定。
2. **可达性必须直接在 yaw_B 上解 IK**,不能用"在不在可达带"—— 可达带是每 5° 采样的,
   边界有 ±5° 假边界(瓶 yaw_B=356.6° 曾被误判带外 1.6°)。
3. **IK 种子必须与 Gate 1 完全一致**(含 `q[3] = −90°` 肘部预弯)。漏了这一行,
   同一个角冷启动报 **18.53cm**(假不可达)、对齐种子后是 **0.10cm**。

### 14.4 结果 + 一条独立证据

| | 对称度 | 人手方位 | A yaw | B yaw | B 处 IK | H3(在**该用的角**上评) |
|---|---|---|---|---|---|---|
| 瓶(右手) | 0.7mm | 216.0° | 120° | **19.5°** | 0.10cm | ✅ 缺口 10.7cm / 姿态差 24° / R_hi 18.8cm |
| 杯(左手) | 3.3mm | 132.8° | 170° | **108.3°** | 0.08cm | ❌ 缺口 20.8cm / **姿态差 165°** / R_hi 33.2cm |

**独立证据**:H3(Gate 1b「人手一致性」,为完全不同目的、很早以前就写好的判据)
对同一个瓶候选 —— **A 下判死**(缺口 24.8cm / 姿态差 119° / R_hi 38.9cm ❌),
**B 下通过**(10.7cm / 24° / 18.8cm ✅)。不是同一条推理的自我印证。

**连带修正**:走 B 时 Gate 1 的 ok/fail **不再当硬门**(它是 A 判据),硬门换成
「B 角可达 + B 角上过 H3」。否则杯会被 Gate 1 以差 0.5° 误杀,而它的 B 角 IK 只有 0.08cm。

### 14.5 待办

  第一条 run 是 `Pour17_bottle`,不受此阻塞。
- 接触带塑形在 B 下不受影响,**已核**:`_aff_pts_local` 与 `aff_local` 都在运行时按物体
  实际四元数变换到世界系(`env.py:1084` / `_target_w`),没有任何世界系常量。

### 15.7 其余锁定项

- **动作**:29 维 `[Δq_arm(7), Δq_hand(22)]`, **保留增量式**。

  每维 μ 动一点点, 联合比就被放大。⟹ **真正的步长闸是 `e_clip=0.2`**, 盘面须同时看 `clip_frac`。
- **左右手共用标定**:`arm_residual_bound.json` 不分左右;手指界标定于 `right`。

**③ ⚠ σ_rot / conf_rot 作废(2026-08-15 夜二次更正 —— 我第一版的解释也是错的)**

我先写的是"6.00° 是 `rts_smoother` 的**上限**截断"。**错。** 重建侧查到成因:
```
rts_smoother.py:284  sig_r_rep = max(滤波σ_rot, degrees(sigma_rot(conf_rot))/2)
                     sigma_rot: conf 100 -> 2° ; conf 0 -> 12°
audit 里 conf_rot 逐帧**全是 0.0**  ⇒  下限 = 12/2 = 6.00°  ⇒  142/142 被钉在**下限**
```
是**下限**, 而且是被一个**坏输入**顶上去的。

**根因: 全局 `pose_audit.json` 被一次"没跑 CoTracker"的运行静默覆盖。**
| 文件 | 时间 | conf_rot |
|---|---|---|
| `confidence_complete.json` | 08-14 17:58 | **68.5 / 52.5**(带 CT 的好记录) |
| `pose_audit.json` | 08-15 00:24 | **0.0 / 0.0**(6.5 小时后被重写) |

全局 40 条记录里 37 条 conf_rot 非零, **pour/17 的两条正是 3 个例外**。
audit 是**全局单文件**且在链里跑两遍(先无 CT 预打分 → 跑 CT → 带 `--ct-dir` 终打分);
任何人事后单独跑一次 `pose_audit.py --scene X` **不带 `--ct-dir`**, 就会把那条
**覆盖成无 CT 版本**, 而 `confidence_complete.json` 早已写完 —— **下游一点都察觉不到**。

⟹ **conf_rot / σ_rot 一律不用**(那不是"旋转不可观测", 是记录被降级)。
⟹ **σ_pos / conf_pos 有效**(audit 的 conf_pos 中位 81.0/84.0 与 manifest 的 80.0/84.0 一致,

**这类坑比"名字骗人"更隐蔽:同一个字段在两个阶段有两种含义, 而后写的赢。**

**④ 已落地的防护**: `load_replay.per_frame_reliability(npz, key)` ——
**任何全片只有一个取值的可靠性字段一律当"无数据"返回 None**, 并打印警告。

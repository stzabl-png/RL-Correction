# 全身遥操作 操作手册

戴 PICO 头显控制机器人的手臂、头和腰,戴手套控制手,在浏览器中查看结果。

本文只说明操作。设计上的取舍与试错过程记录在 `~/magicsim/GR00T-WholeBodyControl/workflow_fj.md`。

本流程只运行仿真,真机与真手都不会动作。

---

## 一、开始前

启动前需完成以下几项。前两项是标定,每次佩戴都需要确认。

### 1. 头显内完成全身校准

在 PICO 系统中走完全身校准流程。判定标准是系统内的人体模型能够准确跟随本人的动作。

未完成校准时,追踪器的数值会全程保持不变,仿真程序会提示需要重做全身校准。

### 2. 手套已标定

手套的标定通过 SharpaPilot 或配套工具完成,不在本流程之内。

标定结束后关闭 SharpaPilot。该程序会占用手套接口,继续开着会导致后续程序报设备被占用或找不到设备。

左手套的拇指标定一直不够准确。若只有拇指不跟随手部动作,通常是手套需要重新标定,而不是程序的问题。

### 3. 手套已佩戴并通电

未佩戴时程序找不到设备,或者能够连上但始终收不到数据。

### 4. 手套网络连通

手套通过网线通信,不使用 USB 串口。可以先确认是否连通:

```bash
ping -c2 192.168.1.101      # 右手套
ping -c2 192.168.1.100      # 左手套
```

如果不通,将手套的 USB 网卡重新插拔一次。

### 5. 头显已开机并开启发送

头显中的 app 填入本机 IP,并打开发送开关。

## 二、启动

只需要一个终端:

```bash
cd <仓库根目录> && .venv/bin/python scripts/vega_console.py
```

浏览器打开 http://localhost:8086,之后的操作都在页面上:

1. 在「控制哪些部位」组勾选:左臂、右臂、控制头部、控制腰部、控制左手、控制右手。
   **控制头部要先勾手臂,控制腰部要先勾头部**;条件不满足时该项是灰的,点不动。
   **控制左手/控制右手(Sharpa)与手臂无关**,各自独立勾选;要用哪只手就勾哪只,
   与勾了哪边手臂没有关系。
2. 「设备」组会显示三行检测结果:Dexmate、Sharpa、相机。有线网口没插时显示「未检测到(有线网口未连接)」。
   相机即使检测到也不会自动连接(外参还没标)。
   检测到 Dexmate 时,页面里的机器人会**自动显示真机当前的实际姿势**(只读,
   不发送任何指令),此时「链路」行显示「仿真未运行 — 显示真机实测姿态」。
   点「启动」仿真跑起来之后,画面自动切换为仿真状态。
3. 「启动」组的**腕部朝向**下拉是一个取舍,只能戴上头显自己判:
   - **绝对(掌心与你一致)** —— 现在的默认,也是 2026-08-01 你在实机上认可的那套:
     机器人的掌心朝你掌心朝的方向。代价是任何手腕姿势都直接换算成绝对角度,
     而机器人腕关节 j6 只有 ±80 度、j7 只有 143 度总量程,人的前臂滚转有
     150 至 180 度 —— 可能超量程,顶死之后朝向就一直是错的。
   - **增量(不易超量程)** —— 只映射「相对这一段起点转了多少」,起点是默认姿势
     (腕关节在量程正中央)。代价是机器人掌心与你的掌心差一个固定角,靠看画面适应。
     **配合「开始新一段」使用**:每段开头归位一次,余量才是满的。
     ⚠ **离线实测并不支持它更不容易超量程**(反而更差),原因很可能出在 PICO 的
     腕朝向重复性上。放在这里是让你能自己戴上头显比一比,不是推荐值。
4. 需要防止手臂撞到桌面时,在「启动」组填**桌面高度**(米,机器人基座为原点,0 表示不用)。
   填了就会自动打开防撞;尺寸填错时启动会当场报错,不会让手臂莫名其妙冻住。
5. 点「启动」。约半分钟后页面中出现机器人,状态各行变为 ✅。
   页面里还会显示**操作者的骨架**,手腕上有两支箭头:白色是掌心朝向,黄色是手指指向。
6. 连接真机、录制数据、停止,都是页面上对应的按钮。上次的勾选会被记住。

「连接手臂」和「连接真手」在**检测不到对应设备时不会启动**,而是在状态行里说明原因(例如「有线网口未连接」)。这样不会留下一个几秒后自己死掉的进程,也不用去翻日志才知道为什么。

「模拟数据」勾上后全部使用合成数据,不需要任何硬件,可用于确认软件链路。

页面右上「全部停止」结束所有子进程;直接关闭终端(Ctrl-C)也会先收干净再退出。各子进程的日志在 `logs/console/` 目录。

原来的多终端方式仍然可用(`scripts/run_teleop.sh`,参数见该脚本头部),两者不要同时开。

## 三、确认状态

页面左侧为各项状态数值,正常运行下显示效果应为:

| 状态行 | 正常显示 |
|---|---|
| 链路 | ✅,其后的数字持续增长 |
| Sharpa 手 | ✅,其后的数字持续增长 |
| 操作者 | ✅,其后的数字持续增长 |
| 操作者掌心 | 与自己此刻的手势相符,例如「左掌下·指前」 |
| 跟随状态 | ✓ 跟随正常,括号内为当前偏差 |
| 顶在限位的关节 | 空。持续显示同一个关节名说明手臂顶住了,见第五节 |

各行都正常时即可开始操作:抬起手臂,机器人的手臂随之抬起;活动手指,机器人的手指随之活动。

「操作者掌心」这一行值得多看一眼:它说的是**系统认为你的掌心朝哪**。如果与你实际的手势不符,说明朝向映射有问题,此时机器人手的朝向也一定不对。

某一行显示 ⚠ 时,只需检查对应部分。手臂与手是两套独立的程序,其中一个停止不影响另一个继续运行。

## 四、停止

```bash
tmux kill-session -t vega
```

Ctrl-C 与 kill -9 会导致显卡驱动异常,此后仿真无法启动,因此停止时不使用这两种方式。

停止后可确认显卡状态:

```bash
.venv-isaac/bin/python -c "import torch;print(torch.cuda.is_available())"
```

输出 `True` 表示正常。若输出 `False` 或报错,使用以下命令恢复:

```bash
sudo rmmod nvidia_uvm && sudo modprobe nvidia_uvm
```

## 五、常见情况

| 现象 | 说明 |
|---|---|
| 手指不动作 | 检查手套所在的窗口。显示 `Device not found` 表示手套未佩戴或未通电,佩戴后程序会自动重连 |
| 手套已连接,手指仍不动作 | 该窗口持续显示 `valid=False`,表示手套没有输出数据,将 USB 网卡重新插拔一次 |
| 只有拇指不跟随 | 属于手套标定问题,左手套一直存在此现象,需要重新标定 |
| 手臂不动作 | 检查仿真所在的窗口,正常时 `engaged=` 之后包含 right 与 left |
| 页面显示断流 | 仿真程序已停止,检查该窗口即可 |
| 显卡报错,而 nvidia-smi 显示正常 | 使用第四节末尾的命令恢复 |
| 需要查看某个窗口 | `tmux attach -t vega`,Ctrl-b 配合方向键切换窗口 |
| 追踪器数值全程不变,提示重做全身校准 | 头显内的全身校准未完成或已失效,重新走一次校准流程 |
| 手掌朝向不再跟随,「顶在限位的关节」显示 j6 或 j7 | 手腕转动超出了机器人腕关节的量程。机器人会停在限位附近继续跟随位置,把手转回可达范围后朝向自动恢复,无需干预 |
| 「顶在限位的关节」持续显示 j1 至 j4 | 手伸出了机器人手臂的可达范围,把手收回一些即可 |
| 设备行提示「本机不在 xxx 网段」,或机器人/真手明明开着却检测不到 | 网口拔插或重启后丢了第二地址。运行 `sudo bash scripts/setup_robot_net.sh` 一次补齐并自检连通性 |
| 报设备被占用或找不到设备 | SharpaPilot 仍在运行,占用了手套接口,关闭后重试 |

手套本身是否正常可单独测试,测试期间需要活动手指:

```bash
PYTHONPATH= .venv/bin/python scripts/diag_glove.py --hand right --duration 12
```

输出末尾两行为各关节的活动幅度。四个指尖在几十毫米量级属于正常,全部为 0 表示手套没有输出数据。

## 六、运行当中的调整

手套掉线或需要更换参数时,只重启手套即可。在手套所在的窗口按 Ctrl-C,重新执行:

```bash
PYTHONPATH= .venv/bin/python scripts/teleop_retarget.py --source wuji --hand right \
  --pinch-weight 20 --relax-distal
```

不需要脱下头显,也不需要停止手臂一侧。

运行中追加一只手需要两个步骤。浏览器所对应的程序只在启动时建立订阅,因此需要重启该程序,否则不会收到新增的这只手。

```bash
# 1. 新开一个窗口,启动左手
PYTHONPATH= .venv/bin/python scripts/teleop_retarget.py --source wuji --hand left \
  --pinch-weight 20 --relax-distal --pub tcp://*:5557

# 2. 重启浏览器所对应的程序,并加上左手地址
.venv/bin/python scripts/viser_isaac_mirror.py \
  --hand-right tcp://127.0.0.1:5556 --hand-left tcp://127.0.0.1:5557
```

重启完成后刷新浏览器页面,同样不需要脱下头显。

### 录制一段数据

**每段开始之前先点「开始新一段」。** 机器人会慢速回到默认姿势,求解器同时归位,然后从那里重新跟随。这一步是为了让每一段都从同一个已知姿势出发——不做的话,上一段结束时手臂是什么姿势,下一段就从那个姿势继续,包括那些别扭的姿势。

之后:

1. 需要的话在「本次名称」里起个名字。留空则按录制的起止时间自动命名。
2. 点「开始录制」,做动作,再点一次停止。
3. 全部数据写在 `data/sessions/<名称>/` 这一个目录里:手臂指令、Sharpa 手关节与触觉、真机各关节、手套原始数据、PICO 数据、点云(相机接了的话)。

录完可以离线合并成一份:

```bash
.venv/bin/python scripts/merge_episode.py data/sessions/<名称>
```

**⚠ 合并出来的数据现在还不能当作严格同步的数据用。** 各路的时间戳是同一个墙上时钟,但各路的采集延迟不同,戳对齐不等于动作对齐。要确认还差多少,录一段「双手快速合拢拍一下」,然后:

```bash
.venv/bin/python scripts/check_clap_sync.py data/sessions/<名称>
```

小于 20 毫秒才可以直接合并。**这一步至今没在真实数据上做过。**

## 七、上真机之前的验证流程

真机第一次连接之前,先用这一套把动作确认一遍。录一段、反复看、确认无误再让机器人重放同一段,而不是一边调试没验证过的硬件一边跟随随时在变的人的动作。

预览、物理复演、真机下发三者用的是同一份指令数据,所以看到的就是机器人会做的。

**第一步,录一段。** 正常遥操作,同时录下要发给机器人的指令。

```bash
.venv/bin/python scripts/replay_check.py --record logs/take_0001.msgpack
```

结束时按 Ctrl-C。它会报出录了多少帧、其中多少帧离合是闭合的。离合从未闭合的录制无法用于驱动机器人,当场就会说明。

**第二步,在浏览器里反复看。**

```bash
.venv/bin/python scripts/replay_check.py --preview logs/take_0001.msgpack
```

循环播放,不接机器人。这一步只看动作对不对。

**第三步,在物理里跑一遍。** 上一步是纯运动学,指令是多少就画多少,永远追得上;这一步才会暴露追不上的关节。

```bash
.venv-isaac/bin/python sim/replay_in_isaac.py --file logs/take_0001.msgpack --headless
```

结果里会点名平均偏差超过 5° 的关节。目前实测最差的是腕部的 j7,平均 3° 左右,属于正常。

**第四步,确认后让机器人重放。** 另一个终端运行桥接程序,然后开始回放:

```bash
~/Dexmate/dexcontrol/.venv/bin/python scripts/dexmate_bridge.py --live
.venv/bin/python scripts/replay_check.py --play logs/take_0001.msgpack
```

回放程序先进入预览,机器人不会动。在页面的「驱动真机」处打开开关,机器人先按 8 度每秒缓慢移动到这段动作的起始姿势,到位后重放一遍,然后自动退回预览。

需要再放一遍时,把开关关掉再打开。开关一直开着不会自动重复。

关闭开关或关掉页面都会立即停止。

## 八、本流程暂不涉及的部分

浏览器中手指的动作不代表实际手部硬件在动作。真手由另一个程序驱动,参见 `SOP.md`。

实时遥操作本身不驱动真机。要让机器人动作,走第七节的录制与回放流程,并且需要单独运行桥接程序。
